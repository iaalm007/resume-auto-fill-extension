# 简历自动投递助手 · MVP

一个 Chrome Manifest V3 扩展：进入投递页面后，**扫描前端输入框 → 规则匹配简历字段 → 自动填充 → 重扫补齐**，最后由用户人工核对并提交。

配套设计文档见 [`简历自动投递Agent-设计方案.md`](./简历自动投递Agent-设计方案.md)。

---

## 目录结构

```
extension/
├── manifest.json              # MV3 清单
├── background.js              # Service Worker（首次安装打开设置页）
├── popup.html / .css / .js    # 人在环路 UI：扫描结果确认与填充触发
├── options.html / .css / .js  # 简历资料编辑页（含文件导入、经历数组编辑）
├── shared/
│   ├── profile-store.js       # 数据层：多份简历 CRUD + 当前使用简历（每份简历一个独立键）
│   ├── ai-config.js           # AI 配置（开关 / 接口地址 / 模型 / Key）
│   ├── ai-map.js              # AI 兜底匹配的核心逻辑（提示词、解析、缓存、白名单校验）
│   ├── bg-message.js          # 与后台通信：重试 + 把「接收方不存在」这类报错翻译成人话
│   ├── file-text.js           # 导入：PDF / DOCX / TXT → 纯文本
│   ├── resume-parser.js       # 导入：文本 → 结构化 Profile（本地规则）
│   └── pdf-loader.js          # 加载 vendor 里的 pdf.js（外部文件，MV3 CSP 禁止内联脚本）
├── vendor/pdfjs/              # pdf.js 精简运行时（pdf.min.mjs + worker + cmaps，约 2.8MB）
├── content/                   # 注入页面的 Agent 核心
│   ├── debug.js               # 诊断日志：控制台 [RJ] 输出 + 内存环形缓冲
│   ├── config.js              # 语义层：同义词词典 / autocomplete / 排除词
│   ├── scanner.js             # 感知层：扫描控件、抽取字段特征包
│   ├── matcher.js             # 语义层：字段 → Profile 路径匹配
│   ├── filler.js              # 执行层：受控组件安全写入
│   └── main.js                # 编排层：扫描→填写→重扫循环
```

分层与设计文档严格对应：**感知层 → 语义层 → 执行层 → 数据层 → 编排层**。

## 安装（加载已解压扩展）

1. 打开 `chrome://extensions/`
2. 右上角开启 **开发者模式**
3. 点击 **加载已解压的扩展程序**，选择本仓库的 `extension/` 目录
4. 首次安装会自动打开「简历资料」页面

> Edge 同理：`edge://extensions/`。

---

## 使用

1. **管理简历**：点击扩展图标 → 右下角「资料设置」，或首次安装自动弹出的页面。
   - 支持**多份简历**：新建 / 复制 / 重命名 / 删除，并指定「当前使用简历」。
   - **导入简历文件**：选一个 PDF / DOCX / TXT，自动抽取并填入草稿，核对后「保存资料」或「存为新简历」。
   - 可先点「填入示例数据」快速体验。数据存于浏览器本地（`chrome.storage.local`）。
2. **选择要投的简历**：在扩展弹窗顶部的「使用简历」下拉框切换，切换后自动重新扫描。
3. **打开投递页面**（真实招聘站点）。
4. 点击扩展图标 → **自动扫描**（打开就有结果，不用手动点）。
5. 点一下 **自动填写 N 项** —— 就这一下。符合条件的字段默认**全部勾好**，不用你挨个选；
   想排除个别字段就取消它的勾选。填完会多出一个 **撤销填写**，点一下就把这次填的撤回去
   （页面回到填写前的样子）。
6. 投递页上**人工核对**后自行点击「提交」——扩展不会替你提交。

## 本地测试页（不想上真实站点也能试）

`extension/examples/` 下有两个页面，直接用浏览器打开即可：

| 文件 | 用来验证什么 |
|---|---|
| **`verify.html`** | **验证台**（推荐）：直接加载扩展里正在用的那几个真实文件（`config` / `scanner` / `matcher` / `filler`），对一批真实表单结构跑一遍扫描、匹配、填充，并把**会发给模型的完整内容**摆出来。打开即跑，不用装扩展、不用点任何东西 |
| `sample-form.html` | 综合场景：受控组件（值会被框架回滚）、选「有工作经验」才出现的动态字段 |
| `sample-form-hard.html` | **标签推断**：label 是单独的 `<div>`、和输入框隔了包装层，输入框只有 `placeholder="请输入"` |

`verify.html` 会自己给出结论（「全对」/「N 处不对」），并逐字段列出抓到什么标签、标签从哪一级来的、
匹配到哪个路径、置信度多少。它对每个字段都有预期值，所以**哪一层坏了会直接标出来**，
不用人去核对。它只覆盖「感知 → 匹配 → 填充」这条确定性链路；
AI 那一环需要真 Key，由 `verify` 之外的端到端测试覆盖。


`sample-form-hard.html` 是照着真实招聘系统的 DOM 结构做的：页面本身不含任何语义信息，
**只有标签推断正确，扫描结果里才会显示「姓名 / 手机号码 / …」而不是「请输入」**。
页面最后一个字段故意不写标签，用来对照 —— 它应当显示「请输入」并带「标签未识别」角标。

## 在真实站点上试

直接拿一个真实的招聘投递页来试即可。几个建议：

- 选一个**需要填基本信息**的页面（姓名 / 手机 / 邮箱 / 学历那类），最能看出匹配效果。
- 打开弹窗先看扫描结果和置信度，**逐条核对**再点填充。
- 匹配不上的字段说明同义词词典缺词条，补 `content/config.js` 的 `fieldRules` 就行 ——
  这是提升效果性价比最高的地方。
- 想看清楚字段为什么会这样匹配，可以打开投递页的 DevTools 控制台，
  扫描结果里每个字段都带 `reason`（命中了哪个关键词）。

> 扩展**不会**自动点提交，也不会绕过登录 / 验证码；验证码出现时请手动填写。

## 出问题了怎么排查

### 方法一：弹窗里的「诊断」按钮（推荐）

弹窗右上角有个 **诊断** 按钮，点一下会把完整现场复制到剪贴板：

- 扫描到的所有字段（标签 / **标签来源** / 类型 / 匹配到的路径 / 置信度 / 命中的关键词 / 页面是否为空）
- **规则没命中的字段的「语境快照」**：逐级祖先元素的类名 + 每一级的「前兄弟文本」，
  再附上控件自身的 HTML（定位「标签到底为什么没找到」主要靠这个）
- 填充报告（哪些成功、哪些失败、失败原因）
- 最近的 `[RJ]` 日志
- AI 是否启用、问了几次、命中缓存几次

直接粘贴给我就行。**诊断包里不含你简历里的任何值** —— 只标了「这个字段简历里有没有值」，
不会把姓名、手机号、邮箱带出去（这条有自动化断言盯着）。

### 方法二：页面控制台

投递页按 F12，控制台里所有日志都带 `[RJ]` 前缀。想实时看扫描过程：

```
[RJ] 19:05:29.250  scanner  {"candidates":12,"accepted":9,"rejected":3,"crossOriginFrames":0}
[RJ] 19:05:29.250  scanner.rejected  ["兴趣爱好 [hidden] <- type=hidden","系统自动填写 [text] <- disabled"]
[RJ] 19:05:29.261  scan  {"total":8,"matched":6,"unmatched":2}
[RJ] 19:05:29.261  scan.unmatched  ["兴趣爱好[text] ph=\"随便写点\""]
```

几条日志的含义：

| 日志 | 说明什么 |
|---|---|
| `scanner candidates/accepted/rejected` | 页面上找到多少个候选控件、接受几个、跳过几个 |
| `scanner.rejected` | **「为什么那个输入框没被扫到」** —— 是 disabled / hidden / 不可见 / readonly |
| `scan` | 扫描汇总：共几个字段、命中几个、没命中几个 |
| `scan.unmatched` | 未命中字段的标签与属性，**一眼看出词典缺什么词** |
| `fill` / `fill.fail` | 填充结果；失败会带上具体原因 |
| `filler.miss` / `filler.error` | 元素失效或写入时抛异常，会带上 selector |

### 常见现象对照

| 现象 | 多半是 |
|---|---|
| 设置页报 `Could not establish connection. Receiving end does not exist.` | 后台没接上。最常见的原因是**扩展刚重载过，而你手上这个设置页是旧的**（旧页面已失效，且跑的还是旧代码）。**关掉设置页重新打开**即可。注意：「测试连接」已改为**直连接口、不依赖后台**，所以这个按钮不会再报这句话 |
| 「测试连接」提示**接口正常、但后台连不上** | 你的 API 配置没问题，是 Service Worker 没起来。**这个不影响使用** —— 投递页的 AI 会自动退到本页直连（见「后台依赖与降级」）。想修的话：`chrome://extensions` 看本扩展卡片有没有「Service Worker」链接（**没有就说明它从未注册成功**），或者干脆**移除扩展再重新加载**（点「重新加载」清不掉坏的注册状态） |
| 开了 AI 但「感觉没什么区别」 | 先看弹窗里那条 **AI 说明条** —— 它会明说「未启用」「配置不完整」「分析了几条补上几条」还是「都没能对应上」。绝大多数情况是**「启用」没勾**（测试连接通过 ≠ 已启用） |
| 「测试连接」报 429 /「已达到速率限制」 | **先看业务错误码**（文案会带上「接口原话」）—— HTTP 429 底下挂着**处置方式完全不同**的原因，别一律当成「额度用尽」：<br>· `1302` **账户维度**的速率限制：当前模型的**并发数**到上限，或短时间内请求过密 → 降并发、让请求排队，或稍等再试。**同一把 Key 若还有别的程序在用，占的是同一个账户的并发额度**<br>· `1305` **平台维度**的过载（「该模型当前访问量过大」）→ **不是你账号的问题**，换账号也一样；稍后重试并拉长重试间隔<br>· `1113` 账户**欠费** → 充值，等多久都没用<br>· `1308` / `1310` / `1316`~`1321` 周期 / 套餐**额度用尽** → 会在接口给出的时间点自动重置<br>· `1309` / `1311` / `1313`~`1315` 套餐到期 / 权限 / 公平使用策略受限<br>并发额度按「用户权益等级 + 具体模型」而定，去控制台看（智谱：`bigmodel.cn/usercenter/proj-mgmt/rate-limits`），要提升可提交速率限制调整申请。<br>依据：智谱官方错误码表 `docs.bigmodel.cn/cn/faq/api-code` 与速率限制说明 `/cn/api/rate-limit` |
| 弹窗提示「**本分钟已发满 N 次请求，本地限流生效**」 | 这不是接口报错，是扩展**主动踩了刹车**（`MAX_PER_MINUTE`），为了不打满接口配额。等提示的秒数即可；若这个上限对你太紧，改 `shared/ai-map.js` 里的 `MAX_PER_MINUTE` |
| 弹窗提示「**接口刚返回过限流，本地已静默 N 秒**」 | 上一次请求真的撞到 429 了，扩展把整个扩展（含所有标签页）静默一段时间。等着就行，别反复点扫描 |
| 弹窗提示「**自动分析刚跑过（X 分钟前），先不重复请求**」 | 这是**正常的省额度行为**，不是故障：同一个站点 10 分钟内不重复自动请求。要现在就跑，点右边那个「让 AI 判断」 |
| 字段标签全是「请输入」，一个都匹配不上 | **标签没抓到**。开启 AI 兜底可由模型从 DOM 骨架推断；不想开 AI 就看诊断包里该字段的 `context`（逐级祖先 + 前兄弟文本），定位断在哪一级 |
| 字段扫出来了但没匹配上 | 词典缺词。看 `scan.unmatched`，把新词补进 `content/config.js` 的 `fieldRules` |
| 字段压根没出现在列表里 | 被判定为不可见/禁用。看 `scanner.rejected` 里的原因 |
| 值填进去了又被清空 | 页面是受控组件且没吃 `input` 事件（少见，需要单独适配） |
| 报「元素已失效，请重新扫描」 | 页面在这期间重渲染了，点一次「重新扫描」即可 |

## 当前已实现（Phase 1）

| 能力 | 说明 |
|---|---|
| 简历管理 | 多份简历增删改查 + 「当前使用简历」切换 |
| 简历导入 | PDF / DOCX / TXT → 文本 → 结构化草稿；全本地解析，文件不上传 |
| 经历数组编辑 | 教育 / 工作 / 项目经历的可增删编辑区块（导入结果直接落进这里） |
| AI 兜底匹配 | 规则没命中的字段连同 **DOM 骨架**一起交模型（解决「标签没抓到」这类感知问题，不只是映射）；返回路径 + 认出的真标签；带路径白名单、**并发 + 每分钟频率双闸**、退避重试、429 全局冷却（可选，默认关） |
| 记忆层 | 模型结果按「站点 + 结构签名」落盘；同一网站第二次访问不再联网，且界面直接显示真标签 |
| 缺失要素记录 | 记下「表单问了但简历里没有」的字段，累计次数并在设置页展示 |
| 新信息回填 | 填表时新补的值可一键写回当前简历 |
| 字段扫描 | 遍历 `input/textarea/select/[contenteditable]`，过滤隐藏/禁用/密码框；穿透同源 iframe |
| label 推断 | `aria-label` → `aria-labelledby` → `label[for]` → 包裹 label → **逐级向上找「祖先的前兄弟」** → **祖先容器自己的文字** → placeholder；同时记录标签来自哪一级 |
| 不过度推断 | 五条闸，都是被真实 bug 逼出来的：①祖先里控件太多就停止上爬（否则会把整表单第一个字段的标签认成自己的）；②容器语义只取**直接子文本节点**（否则校验提示「此项必填」会被当成字段名）；③校验/提示类文字不认；④**自定义组件内部不取兄弟**（否则下拉/日期组件会把自己的「当前选中值」当标签 —— 实测北森的表单：「学历」被读成「硕士研究生」、「出生日期」被读成「2002-02-01」）；⑤**看起来像值的文字不认**（日期、纯数字、`0/2000` 字数比、邮箱、手机号） |
| 标签可信度 | 只靠 placeholder 兜底时弹窗会打「标签未识别」角标 —— 这时显示的「请输入」是假标签，匹配不可信 |
| AI 状态可见 | 未启用 / 已启用但配置不全 / 分析了几条补上几条 / 认出来但简历里没有 —— 都常驻在弹窗上，不会静默什么都不做 |
| 语义匹配 | 规则层：autocomplete 标准名 > label/placeholder 关键词 > name/id 关键词；支持排除词、最长关键词优先 |
| 受控组件写入 | 原生 setter + `input`/`change`/`blur` 事件派发 |
| 特殊控件 | select 文本/值匹配、单选/复选组（精确优先，避免 `Java` 误命中 `JavaScript`）、contenteditable |
| 重扫循环 | 填写后最多 2 轮重扫，自动补齐新出现的、置信度达标的字段 |
| 人在环路（一键） | 符合条件（空字段 + 已匹配 + 简历有值）的行**默认全部勾选**，主按钮直接写「自动填写 N 项」，点一次就填完，不用挨个选；一项都没有时按钮变灰并**说明原因**（页面已有内容 / 简历缺值 / 被你取消勾选）——不解释的话用户只会以为功能坏了。填完可**一键撤销**。页面已有内容只提示不覆盖；提交始终交给用户 |

## 简历数据是怎么存的

**每份简历占一个独立的 storage 键**，`rj_active_resume` 只存一个指针：

```
rj_resume_r_a1b2c3 : { id, name, profile, createdAt, updatedAt }   ← 简历甲
rj_resume_r_d4e5f6 : { id, name, profile, createdAt, updatedAt }   ← 简历乙
rj_active_resume   : "r_a1b2c3"                                     ← 当前使用哪份
```

读取时用 `chrome.storage.local.get(null)` 把所有 `rj_resume_` 前缀的键捞出来，按 `createdAt` 排序。

**为什么不用「一个键存整个数组」**：那种写法每改一份简历都要把整个数组重写一遍。
实测对比（一份简历约 4KB）：

| 操作 | 单键存数组（旧） | 一份简历一个键（现） |
|---|---|---|
| 只切换「使用简历」 | 写入 3263 字节 | **写入 38 字节** |
| 再加一份简历 | 写入 9740 字节 | **写入 3362 字节**（只写新增那份） |

除了省写入量，更重要的是**并发安全**：两个扩展页面同时改不同的简历时，
旧写法会各自拿着「自己读到的整个数组」去覆盖，后写的赢、先写的改动丢失；
新写法两份简历写的是不同的键，天然互不干扰。

另外编辑页做了脏检查：内容没变就**一次都不写**（连点两次「保存资料」会提示「无改动」）。

> 这是格式变更：旧格式的 `rj_resumes` 键不再被读取。如果你之前已经存过数据，
> 在 `chrome://extensions/` 里对本扩展点「清除数据」重新来一次即可。

## 简历导入是怎么做的

全部在本地完成，不联网、不上传文件：

```
用户选文件
   ↓
file-text.js      按扩展名/魔数判断类型
   ├─ PDF  → pdf.js（vendor 内置，主线程 + worker）逐页取文本，按坐标还原行
   ├─ DOCX → 浏览器原生 DecompressionStream 解 ZIP → 抽 word/document.xml 文本
   └─ TXT  → 直接读
   ↓
resume-parser.js  纯文本 → 结构化 Profile（正则 + 章节切分 + 版式启发式）
   ├─ 先做字符归一化（这一步最关键，见下）
   ├─ 按章节标题切分：教育经历 / 工作经历 / 项目经历 / 专业技能 / 自我评价
   ├─ 基本信息在全文里找：手机、邮箱、身份证、姓名、性别、出生、城市、微信
   └─ 每条结果带置信度
   ↓
options 页 → 填入草稿 → 低置信度字段标黄 → 用户核对 → 保存 / 存为新简历
```

### 一个关键坑：PDF 抽出来的汉字可能是「部首码点」

很多 PDF 的 `ToUnicode` 映射会把汉字输出成部首，例如「黄」变 `⻩`(U+2EE9)、「西」变 `⻄`(U+2EC4)、
「工」变 `⼯`(U+2F2F)。这些字符不在 `U+4E00–U+9FA5` 区间里，会让所有中文正则集体失配，
表现为**一个字都识别不出来**。

处理方式（`resume-parser.js` 的 `normalizeText`）：

1. **NFKC 归一化** —— 还原康熙部首区（U+2F00–U+2FDF）、全角字符、兼容汉字
2. **手工等价表** —— CJK 部首补充区（U+2E80–U+2EFF）NFKC 不处理，内嵌了 Unicode
   `EquivalentUnifiedIdeograph`（UAX #44）的映射表来还原

### 已知限制

- **扫描件 / 图片型 PDF 不支持**：没有文字层，提取会返回空，界面会提示（需要 OCR，未做）。
- **结果只能当草稿**：本地规则解析对版式敏感，请务必核对后再保存。
- **技能是碎片化的**：技能章节常是长篇描述（「熟悉 A、B、C，具备……经验」），
  目前只能按分隔符切分后清洗，质量一般，需要人工整理。
- **只覆盖 5 个章节**：论文、获奖、证书等章节未纳入 Profile 结构（表单一般也不问）。
- **跨源 iframe 的表单仍不支持**。

## AI 辅助匹配（可选，默认关）

规则层能覆盖大部分常见字段，但**手写 DOM 规则不可能覆盖所有公司**——每个招聘系统的表单结构都不一样。
而且规则层失败最常见的原因并不是「词典缺词」，而是**标签根本没提取到**：
页面上每个框都只有 `placeholder="请输入"`，规则层拿到的是一串没有信息量的字。

所以 AI 层要解决的是**感知**，不只是**映射**：

```
① 规则层   词典命中 → 直接用                      0 成本、0 延迟
② AI 层    未命中 → 连同该字段的 DOM 骨架一起问一次模型
③ 记忆层   问过一次就记住（路径 + 模型认出的真标签） → 同一个网站第二次访问 0 请求
```

记忆层的两条规则（都踩过坑）：

- **肯定结论长期有效**：字段 → 路径的映射不会因为时间变错，缓存在就永远命中。
- **否定结论只活一天**（`NEGATIVE_TTL_MS`）：「这个框问的东西简历里没有」如果永久缓存，
  用户去资料页补上之后回来重扫，界面还是「简历里没有」，只能手动清缓存才能修 ——
  单向前门。所以过期就重问一次；`countCached` 用同一套判定，
  否则弹窗会以为「全在缓存里，不用联网」，结果真的发了请求。

只有 ② 需要动到模型，且**只有规则没命中的字段才会带上 DOM 骨架**（骨架占 token，
已命中的字段不给）。

### AI 层到底发什么、模型回答什么

给每个未命中的字段附一份「骨架」——从它自身往上每一层的标签名、类名、
**前置兄弟的文本**和**该层剥掉控件后剩下的文字**：

```
第0层 <input.el-input__inner> 前兄弟[无] 自身文本=""
第1层 <div.el-form-item>      前兄弟[div="手机号码"] 自身文本=""
```

标签通常就藏在「前兄弟」里；`<div>姓名<input></div>` 这类结构只有「自身文本」才有线索。
另外还会附上**本页已被规则解出的字段**（`resolvedExamples`），
它展示了这个网站的标签书写习惯，模型可以据此对失败的字段做类比推断 ——
现实里同一页面的标签位置是有规律的，这个信号比任何单条规则都好用。

模型返回三样东西：

| 字段 | 说明 |
|---|---|
| `path` | 该填简历里的哪个字段（必须在白名单内，或 `null`） |
| `label` | **它认出的这个框真正在问什么** |
| `confidence` | 把握程度 |

`label` 很关键。它有两个用途：一是**替换界面上那个假标签** —— 从此不再显示「请输入」，
而是「紧急联系人手机号」，你一眼就知道该不该手填；二是**写进缓存**，
这个网站下次访问直接命中，不再联网。

即使 `path` 是 `null`（简历里确实没有对应内容），`label` 依然会被保留和缓存 ——
「模型认出了含义但没有可填的字段」和「模型也不知道在问什么」是两回事，前者是有价值的。

主要差别是**要不要绑卡充值**，而不是真花多少钱。

### 隐私边界

发出去的是**页面上的字段标签 + 该字段周边的 DOM 结构**（祖先的标签名/类名、
前兄弟文本、剥掉控件后的剩余文字），以及本页已被规则解出的字段的标签。

**不发的东西**：

- 输入框里的任何 `value`、`checked`、`<textarea>` 内容 —— 这条不只是隐私，
  更是为了**防止模型被你自己已填的数据带偏**：表单里预填了「张三」，
  模型就倾向于把「紧急联系人姓名」判成 `basic.name`
- 简历里的任何内容

> 实现上有个容易踩的坑：`<textarea>` 的 **文本内容就是它的值**，
> 用 `clone.textContent` 取「自身文本」会把你打的字原样带出去。
> 骨架取文本统一走一个「先剥掉所有控件再读」的函数。这条有自动化断言盯着。

API Key 只存在本机浏览器的 `chrome.storage.local` 里，且调用放在后台 Service Worker，
不会进到目标网站页面环境。

### 安全兜底

- **路径白名单**：模型只能选 schema 里真实存在的路径，编造的路径直接丢弃并计入诊断
- **允许弃权**：提示词明确要求「骨架里找不到可靠依据时 path 给 null、confidence 给低分」，
  比逼它硬猜一个好
- **失败不影响主流程**：没配 Key / 超时 / 返回格式不对 → 静默退回纯规则结果
- **并发控制**：后台用信号量限制同时在飞的请求数（`MAX_CONCURRENT`，当前为 **1** ——
  官方限流的口径就是「并发数」，设成 1 最不容易撞 1302）。
  开多个标签页批量填时，这是防 429 的第一道闸
- **限流退避**：**429 默认不重试**。速率限制不是网络抖动 ——
  一秒内重试必然还是 429，而且每次重试都在继续消耗本就见底的配额，**越重试越糟**。
  只有服务端明确给了 `Retry-After` 且不超过 5 秒时才等一次，否则直接把错误交给用户。
  5xx / 网络错误 / 超时会自动重试（最多 3 次，指数退避 + 抖动）；
  401 / 400 / 404 这类参数错误不重试
- **错误翻译按业务码分支**：接口报错各家格式都不一样，而**同一个 HTTP 状态码下面
  可能挂着处置方式完全相反的原因** —— 智谱的 429 底下就同时有 1302（账户并发超限）、
  1305（平台过载）、1113（欠费）、1308 / 1310（额度用尽）……
  所以这里**先认业务码**，再按 HTTP 状态码与关键词兜底，并且每条都把**接口原话**带上
  （那是唯一的证据）。401 说「Key 无效或过期」，404 说「接口地址或模型名不对」。
  没有业务码时**刻意不猜**额度或欠费 —— 猜错方向会把用户引到反方向
  （依据：智谱官方错误码表 `docs.bigmodel.cn/cn/faq/api-code`）
- **测试按钮防连点**：测试期间禁用按钮 + 并发闸。对着有速率限制的接口，
  连点几下就是好几倍的请求，这足以自己把自己打限流
- **频率闸（跨标签页）**：`MAX_PER_MINUTE = 8`，状态存在 `chrome.storage.local` 里。
  为什么还需要第二层：并发上限是**账户维度**的，而我们的信号量是**每个上下文一份**
  （后台 SW、每个直连的弹窗各算各的）—— 多开几个标签页，账户维度就不止 1 个并发了。
  这道闸按「每分钟总量」兜一层，也保证撞过一次之后不再持续往见底的配额上打。
  说明：它**不是照官方数值设的**（官方速率限制文档只定义了「并发数」这一个口径，
  没有给 RPM / TPM），属于本扩展自己的保险。
  为什么要放存储而不是内存：内存态只在「所有请求都走后台 SW」时成立；一旦 SW 被回收，
  或弹窗降级成**本页直连**，每个标签页就各有一份计数。
  放进存储才能做到「跨标签页 + 跨 SW 重启」共用同一个额度
- **429 全局冷却**：接口返回 429 后写一个 60 秒静默期到存储，**所有上下文**
  （含直连的标签页）读到都会停下来。这是唯一能覆盖「直连时各自为政」的兜底手段。
  注意冷却只在**不再重试**时才写 —— 服务端给了短 `Retry-After` 要重试的那次不能写，
  否则会把自己也锁在外面
- 已知不足：跨标签页的 read-modify-write 不是原子的，多个标签页同一瞬间开弹窗时
  可能略微超出上限几个。不引入分布式锁（成本不划算），靠上面的 429 冷却兜底
- **自动跑 AI 有节流**：扫描后仍会自动跑（否则样样都要手点，体验很差），但分两种情况：
  - **缓存全热** → 照跑不误。这一趟是 **0 请求**，还能把上次学到的真标签显示回来，纯赚
  - **有冷字段** → 同一个站点 **10 分钟内只自动跑一次**。窗口内再打开就只显示
    「有 N 个字段规则没认出（M 个已有结论）。自动分析刚跑过（X 分钟前），先不重复请求」，
    并给出一个 **「让 AI 判断」按钮**让用户显式触发（显式触发仍要过频率闸，绕不过去）
  为什么必须这么做：弹窗一打开就 `scan()`，而扫完就自动跑 AI ——
  不拦的话「反复开关弹窗」等于反复发请求，**而用户在界面上完全看不到这件事在发生**
- **缓存（记忆层）**：按「标签 + placeholder + 类型 + 候选项」做指纹，命中就不发请求。
  标签可信时该指纹跨站点通用（「姓名」在所有网站共用一条缓存）；
  **标签不可信时（只有 `placeholder` 兜底）额外掺入「站点 + 结构签名」** ——
  不带结构会碰撞（页面上所有未识别字段的标签都是「请输入」，
  第一个字段的答案会被套到其余全部字段上）；不带站点会让两个用同一套 UI 框架的网站互相认错

**结构签名必须是稳定的**，否则缓存等于不存在、每次扫描都白问一次模型（配额很快见底）。
这条有两处讲究，都是实测踩出来的：

- **排除会随交互变化的 class**（聚焦 / 校验 / 已填写 / 展开…）——
  AntD、Element UI 这类框架最爱往元素上加减状态类，不排除的话用户一聚焦签名就变
- **每一级都固定带上 `:nth()`**，而不是「有多个同类兄弟时才带」——
  否则页面上一插东西，原本唯一的那个元素会突然长出 `:nth(1)`，签名跟着变

### 后台依赖与降级

AI 调用原本都放在后台 Service Worker 里（那里能跨标签页统一排队、共享缓存）。
但 MV3 的 SW 会被回收，某些环境下甚至一直注册不上 ——
这时候报出来的是 Chrome 的一句原文：
`Could not establish connection. Receiving end does not exist.`

**这句话不该让功能不可用，也不该让人看不懂**，所以三层都做了处理：

| 位置 | 行为 |
|---|---|
| 设置页「测试连接」 | **直连接口，不经过后台** —— 它要回答的是「我配的接口通不通」；后台状态单独探一次、单独报，两者不互相掩盖 |
| 设置页「清空缓存」 | 同样直接完成（缓存在 `chrome.storage.local`，两边都能读写） |
| 投递页弹窗 | **优先走后台，后台不在就本页直连** —— 同一套提示词、同一份缓存、同样的隐私边界 |

降级的代价说清楚：直连时多个标签页各发各的，**跨页面的总量控制没有了**（单页内仍有限流与 429 退避）；
而且弹窗被关掉会中断请求，走后台则不受影响。所以后台能用时仍然优先走后台。

诊断包里会记下这次用的是哪条路（`ai.via` = `bg` / `direct`），以及后台不可用的原文。

## 缺失要素与回填

投递时经常遇到「表单问了一个信息，但简历里没填」。这类字段会被记下来，形成闭环：

- **记录**：点「自动填写」时，把「有明确对应字段、但简历里为空」的记进 `rj_missing_fields`，累计被问次数
- **回填**：如果你这次在弹窗里手动补了值，填充后会出一条「有 N 条简历里还没有的信息，要补进去吗？」，
  点一下写回**当前使用简历**
- **查看**：设置页「常被问到、但简历里还没有」清单按被问次数排序，点「去填写」跳到对应输入框；
  已经补上的会标「已补齐」

回填只写入你确认过的路径，**不会覆盖简历里已有的值**（有值的字段根本进不了这个清单）。

## 验证情况

已用脚本在真实 Chrome 中跑通以下链路：

- **验证台页面**（27 项，`examples/verify.html`，打开即跑）：
  真实表单结构 → 真实 `scanner`/`matcher`/`filler` → 逐字段判定对错 → 执行填充 → 检查受控组件。
  还带一个「模拟前端状态变化后再扫」按钮，用来演示**指纹稳定性**
  （加聚焦类、加填写类、插校验提示之后，指纹必须一个都不变）
- **指纹稳定性**（3 项）：模拟聚焦 / 填写 / 校验失败 / 插错误提示之后重新扫描，
  弱标签字段的指纹必须与首次完全一致 —— 这直接决定 AI 缓存能否命中、会不会重复请求

### 测试套件固定在仓库里：`tests/`

一条命令跑完（单元 + 界面 + **真实投递页门禁**）：

```bash
cd tests
node run-all.js          # 全部，约 3 分钟
node run-all.js --fast   # 只跑单元，约 30 秒
node run-all.js --only=real-site   # 只跑门禁
```

**`real-site/form-fill.test.js` 是门禁：每次改动后、继续下一步之前必须过。**
它跑的是**真扩展 + 真投递页 + 真登录态**（通过扩展自己的消息通道
`RJ_SCAN` / `RJ_FILL` / `RJ_CLEAR` 驱动，不是手工注入脚本），验四件事：

| 段 | 验什么 |
|---|---|
| **A** 感知与匹配 | 字段扫得到、标签读得到；`期望工作城市` 落到 `basic.expectedCity` 而**不是** `basic.location`（两者只差两个字，最容易串）；现月薪 / 期望月薪不互换 |
| **B** 组件执行 | 自定义下拉 / 地区选择器能清空、能选上，且扫描器能读回显示值 |
| **C** 端到端 | 按简历填空白字段；另有一条确定性的「清空某个真输入框 → 按简历填回 → 读回一致」，保证这一段不会因为「页面上正好没有空字段」而空转 |
| **D** 安全红线 | 页面上**原有内容**的字段，全程一个字符都不能变 |

三条设计硬规矩：**自己造状态**（用得上的字段先清空再填，跑完还原或清掉）、
**失败也要还原**（清理放在 `finally`，断言失败不会把测试值留在你的表单上）、
**清理优先走扩展**（扩展清不掉的用 CDP 真实鼠标兜底，并标明用了哪条路）。

退出码 **0** 全过 · **1** 有失败 · **2** **没跑成**（环境不具备，没验证任何东西 ——
`2` 特意和 `1` 分开：门禁最怕的不是报错，而是看起来通过了其实什么都没跑）。

## 自定义组件填充

真实站点上「期望薪资 / 期望城市 / 到岗时间 / 学历 / 起止时间」这类字段几乎都不是原生控件，
而是组件库自己实现的下拉。**往它的内部 input 写值是无效的** —— 值归组件自己的状态管，
组件会把写进去的值丢掉（实测北森的表单：写入后读回为空）。
所以走这条路：模拟点击展开浮层 → 在浮层里按文字找目标项 → 点它 → 核对组件**显示出来的值**。

关键是不写站点特定规则，靠通用判据：

| 环节 | 判据（都不依赖类名） |
|---|---|
| 是不是组件 | 逐层上溯找 `role="combobox"`，或类名像 select / picker / cascader 的容器 |
| 面板在哪 | 挂在文档上的浮层 —— **脱离文档流 + 有 z-index + 够大**，且**紧贴触发控件** |
| 哪些是选项 | 浮层里的短文本叶子；排除面包屑 / 页签 / 清除按钮 / 禁用项（**连祖先一起看**） |
| 点哪个元素 | 树形条目里**有复选框就点复选框**（点文字是「下钻」，不是「选中」） |
| 值在哪 | 读组件**显示的文本**（`input.value` 往往是空的），并跳过隐藏的量宽辅助节点 |

几个实测踩出来的坑（细节都写在 `filler.js` 的注释里）：

- **面板是开关式的**：已经开着时再点一下是把它关掉。所以点之前先看有没有开着的，开着就直接用。
- **不需要「可信事件」**：实验确认这类组件只响应普通合成的 click，
  所以真实扩展（派发不了 `isTrusted` 事件）在页面内就能驱动它们 —— 这条路是通的。
- **点一次不够**：页面上常还开着**别的字段**的面板，第一下点击会被拿去关那个；
  关闭还带动画，**动画期间的点击会被忽略**。所以要「点一下、等一等、再判定」，一旦打开立刻停手。
- **热区随状态变**：空的时候热区是内部那个 input，有值之后组件把它换掉、热区就变了。
  用 `elementFromPoint` 取控件中心点上真正在最上层的元素，等于「用户点哪就点哪」。
- **组件选中后会重渲染、把内部元素换掉**：拿旧的元素引用去点、去读全会落空
  （第一版就因此把**已经成功**的填充误判成失败）。**全程用稳定的组件根**。
- **填好的组件内部可能已经没有 input 了**：只按原生控件去找，这类字段会整个从扫描结果里
  消失 —— 用户反而看不到自己填了什么。所以扫描时补一趟「内部无控件的组件根」。
- **CSS `:hover` 合成不了**：组件库的「清除图标」常靠 `:hover` 才显示，
  合成事件触发不了 —— 这是合成事件的天然边界，不是 bug。
- **排除规则别用会误伤的正则边界**：排除「页签」时写成了 `(^|[-_])tab`，
  它**把 `-table` 也一起匹配掉了** —— 日历里整张日期表格的格子全被当作页签排除，
  于是日期字段一律报「点开后没有出现选项浮层」。边界要写成 `tab` 后跟分隔符或结尾。

### 日期 / 月份选择器

日历面板和普通下拉完全不同：里面**没有「能按文字点中的选项」**，只有翻页按钮和年/月/日格子。
所以按「值长什么样」分流（`2024-09`、`1998-03-12` 这类才走），再按可靠性从高到低试两条路：

1. **面板里那个日期输入框** —— AntD / Element / 北森 都会在面板顶部放一个可直接输入的框。
   写值 + 回车最稳，也最不依赖 DOM 细节（实测北森的「出生日期」走这条，一次成功）。
2. **翻到目标年 + 点月（+ 点日）** —— 没有输入框时，先按「上/下一年」按钮把年份拨对，
   再点「9月」这样的格子；日粒度再点日期格。一个年份可能有多个「下一年」按钮
   （日视图一个、月视图一个，隐藏的那个不可见），所以**点完要验证年份真的变了**，没变就换下一个。

这里踩到一个很隐蔽的坑：**面板会延迟约 600ms 才挂进 DOM**。
只在点击后单点看一眼（比如等 950ms 再看）会正好错过，于是把「能填」误判成「点不开」，
白绕了很久。现在改成 300 / 600 / 900ms 分层采样，并且把**未做任何过滤的大浮层数**也记进日志 ——
这样才能区分「面板压根没渲染」和「渲染了但被过滤条件筛掉」，这两种情况的修法完全相反。

## 真实流程端到端（在调试浏览器里跑的）

做法：用 CDP 的 `Extensions.loadUnpacked` 把扩展装进一个专用 profile，再从**扩展自己的页面**
发消息（`RJ_PING` / `RJ_SCAN` / `RJ_FILL`）驱动它。这样跑的是真正的 content script、
真正的扫描/匹配/填充，而不是手工往页面里注入脚本。

| 步骤 | 结果 |
|---|---|
| 导入真实简历 PDF（722KB） | 本地解析 3278 字 → 姓名 / 手机 / 邮箱 / 生日 / 现居 / 教育 2 / 工作 2 / 项目 2 / 技能 29 |
| 点「保存资料」 | 「已保存」，落盘成功 |
| 投递页扫描 | 29 个字段，规则命中 12 个 |
| 填充 | 3 个空字段全部填入成功；页面上**已有内容的「手机号码」被正确跳过** |
| 回读核对 | 姓名 / 邮箱 / 出生日期 都在，没有被受控组件回滚 |

### 顺带修掉一个用户可见的真 bug：导入的简历从未落盘

导入简历后，界面提示「核对后点右下角「保存资料」」，但点下去只会显示 **「无改动」**，
**导入的内容一个字节都没写进存储** —— 界面看起来一切正常，最坏情况是用户以为存好了。

原因：`fillForm()` 结尾会把当前表单内容记进 `state.savedJson`（本意是给「切换简历时判断有没有改过」用），
而 `saveCurrent()` 正是拿 `collect()` 和它比对来决定要不要写盘。于是「用 `fillForm` 灌入新内容、
再让用户点保存」这条路 —— 内容刚灌进去就已经被记成「已保存」了。
修法：灌完显式标记为脏（`markDirty()`）。**「填入示例」那条路有完全相同的问题，一起修了。**

## 重复区块（教育 / 工作 / 项目经历）

投递页上这些字段按「块」重复出现，块与块之间标签完全一样（每块都有「开始时间」）。
**光看标签分不出属于第几段**，所以路径里只写 `[*]`，由内容脚本按 DOM 顺序切块：

| 环节 | 做法 |
|---|---|
| 规则层 | 规则只说「属于哪一类块」；`anchor: true` 的是块的起点（学校名称 / 公司名称 / 项目名称） |
| 段号 | 遇到锚点 → 该类型段号 +1，并把「当前块」切过去；之后的中性字段（开始/结束时间、职责、描述）归当前块 |
| 加行 | 简历里的段数比页面上的行多时，点该区块的「+ 添加」（最多 3 次/次填写），**加一行就重扫一次**核对真的多了一行 |
| AI | 模型只返回 `education[*].school` 这种模板，**不许自己写序号**；弹窗拿到模板后回内容脚本解析成 `education.1.school` |

为什么 AI 不能自己写序号：它看到的是一批字段，不知道「开始时间」在页面上属于哪个块。
让它猜必然错位，而错位的症状是「第 2 段的公司填进了第 1 段」—— 用户未必看得出来。

`tests/unit/block-rows-test.js` 覆盖这条链路：段号分配、自动加行、加完把新行填上、
AI 模板解析。真实投递页上页面默认只渲染已有经历，所以自动加行需要「清掉一行 + 简历里多一段」才会触发。

## 尚未实现（下一步）

- **自定义组件填充只剩一类没通**（普通下拉、地区选择器、日期/月份选择器都已做通，
  见下「自定义组件填充」）：
  - **期望行业 / 期望职业** —— 点开不弹面板，疑似要先输入搜索，或与上级字段有级联依赖
- **清空多选型组件不够稳**：地区选择器没有「清除图标」，只能靠面板里的
  「清空已选 + 确定」。这条依赖面板恰好能打开，实测偶发失败（面板是开关式的，
  点多了会把它关回去）。填充是稳定的，清空是次要操作，先记在这里。
- **操作地区选择器会明显卡顿**（真实投递页门禁里最慢的一步）：清空或选定
  「期望工作城市」之后，站点要重画 99 个省 / 区的列表，**页面主线程会被占住
  十几秒到几十秒**（期间 `chrome.tabs.sendMessage` 的响应都回不来）。
  这是站点自身的重渲染成本，扩展侧规避不掉；目前至少做到不把它当失败
  （CDP 单条命令超时给到 90 秒）。要真正改善得想办法绕开整表重渲染，优先级不高。
- **附件上传还没做**：投递页几乎都要传简历附件，`input[type=file]` 目前完全不处理 ——
  这一步只能手动。要做需要构造 `File` 塞进 `DataTransfer`（简历原文/PDF 已经在扩展里，拿得到）。
- **「+ 添加」按钮是启发式的**：识别方式是按文本（添加/新增 + 教育/工作/项目）从锚点往上爬，
  再退化到整页找。换一套 UI 框架、或者按钮只有图标没有文字（aria-label 也空）就会找不到 ——
  这种情况会如实报「没找到添加按钮」，不会乱点。真遇到再补对应的文本/类名即可。
- **记忆层还差一半**：现在记住的是「模型判定」（字段指纹 → 路径 + 真标签），
  但**用户的手动修正**还没记 —— 你改过一次的字段，下次应该直接按你的改法来，
  而不是继续问模型。这一层比模型判定更值得沉淀。
- **简历解析接入 LLM**：现状是纯本地规则。经评估收益有限（简历本身缺的信息，模型也变不出来），
  暂不做；如果以后遇到版式特别怪的简历再说。
- **扫描件 OCR**：图片型 PDF 目前无法导入。
- **跨源 iframe**：需要把 content script 设为 `all_frames: true` 并做按 frame 的路由。
- **多步/分页表单**：跨页面的填充分段编排。

## 注意事项

- 扩展**只往表单里填内容**：提交、暂存、保存、预览一个都不点 —— 页面上「添加教育经历」这类
  加行按钮是唯一会主动点击的东西（不点就没有地方填第 2、3 段），其余保存动作全部归用户。
  代码里也据此设了黑名单（`scanner.js` 的 `NOT_ADD_RE`），否则「添加并暂存」这种文案
  会让扩展替代用户保存，而用户毫不知情。
- **填完不等于保存**：内容还在页面的内存里，用户不点「暂存/提交」就刷新的话会全丢。
  弹窗的完成提示会明说这一点。做真实站点验证时也要记住这条 —— 别为了「还原页面」去刷新，
  先暂存再试，或者干脆用一个无关的测试岗位。
- 资料（含手机号、身份证号等）仅存浏览器本地，未上传云端；导入解析同样全本地。
- 页面上已有内容的字段默认不勾选，避免覆盖你已填信息。
- **换电脑 / 挪动扩展目录会丢数据**：未打包扩展的 ID 由目录路径推导，路径一变 ID 就变。
  需要长期使用建议在 `manifest.json` 里加固定的 `key`。
